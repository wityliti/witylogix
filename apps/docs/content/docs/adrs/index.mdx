# Architecture Decision Records

Architecture Decision Records (ADRs) document the important architectural decisions made during the development of Witylogix. They capture the context, decision, and consequences of each choice.

## What Are ADRs?

An ADR is a short text file in a specific format that documents an important architectural decision, the reasoning behind it, and the consequences of that decision.

**Benefits of ADRs:**
- **Clear reasoning**: Understand *why* decisions were made, not just *what* was decided
- **Future reference**: Avoid revisiting old debates
- **Onboarding**: Help new team members understand the platform's architecture
- **Accountability**: Track who made decisions and when
- **Evolution**: Show how the platform evolved over time

## How to Propose a New ADR

### Step 1: Identify a Decision

An ADR should document decisions about:
- Architecture patterns and styles
- Technology choices (frameworks, libraries, tools)
- Design principles
- System structure
- Integration approaches

**Good candidates:**
- "Should we use microservices or monolith?" ✅
- "Which database: PostgreSQL or MongoDB?" ✅
- "Event-driven or request-response?" ✅
- "Implement real-time notifications via WebSocket or polling?" ✅

**Not suitable:**
- Code style decisions (use ESLint config instead)
- Project management processes (use team docs)
- Minor implementation details

### Step 2: Gather Context

Before writing, discuss with the team:
- What problem are we solving?
- What are the alternatives?
- What are the trade-offs?
- Who will be affected?

### Step 3: Write the ADR

Use the template below. Keep it concise (1-2 pages).

### Step 4: Submit for Review

1. Create a pull request with the new ADR
2. Link to relevant issues or discussions
3. Tag relevant team members for feedback
4. Update the ADR based on feedback
5. Merge once consensus is reached

### Step 5: Document the Decision

Once merged, the ADR becomes part of the official record. Reference it in code comments, documentation, and architecture discussions.

## ADR Template

Create a new file `adr-XXX-{title}.md` in the `/docs/adrs/` directory.

```markdown
# ADR-XXX: {Title}

## Status
Accepted | Pending | Superseded | Deprecated

## Context
Explain the issue or decision that prompted this ADR. What are we trying to solve?

## Decision
State the architectural decision that was made, clearly and concisely.

## Rationale
Explain why this decision was chosen over the alternatives. What are the trade-offs?

### Alternatives Considered
- **Alternative 1**: Why this was rejected
- **Alternative 2**: Why this was rejected

## Consequences
What are the positive and negative consequences of this decision?

### Positive
- Benefit 1
- Benefit 2

### Negative
- Trade-off 1
- Trade-off 2

## Related ADRs
- ADR-XXX: Related decision
- ADR-YYY: Related decision
```

### Example ADR

```markdown
# ADR-005: Use Event-Driven Architecture for Order Processing

## Status
Accepted

## Context
The order processing system needs to handle multiple steps: inventory reservation, payment processing,
notification sending, and shipment creation. Currently, these are tightly coupled in a single synchronous flow,
making it difficult to add new steps or handle failures gracefully.

## Decision
Adopt an event-driven architecture where each step publishes events that trigger the next step asynchronously.
Use RabbitMQ as the message broker and Node.js/Fastify as the event consumer.

## Rationale
- **Decoupling**: Each service only cares about events, not implementation details
- **Scalability**: Easy to add new steps without changing existing code
- **Resilience**: Failed steps can retry independently without cascading failures
- **Observability**: All events are logged, making debugging easier

### Alternatives Considered
- **Synchronous API calls**: Coupled, harder to extend, cascading failures
- **Kafka**: Overkill for our scale, more operational overhead
- **AWS SQS**: Would lock us into AWS, increases vendor dependency

## Consequences

### Positive
- New features can be added by subscribing to events
- Better error handling and retry logic
- Easier testing with event mocking
- Improved observability

### Negative
- Eventual consistency instead of immediate feedback
- Debugging distributed events is more complex
- Need to manage message broker infrastructure
- Higher latency (events processed asynchronously)

## Related ADRs
- ADR-009: Event Bus Implementation
- ADR-010: Real-Time Notifications
```

## Detailed ADRs

### <a id="adr-001"></a>ADR-001: Monorepo Structure with pnpm Workspaces

**Status**: Accepted | **Date**: 2024-01

Organize the Witylogix platform as a monorepo using pnpm workspaces. Allows multiple packages and applications to coexist while sharing dependencies, types, and configuration.

**Key Benefits:**
- Shared TypeScript types across apps
- DRY principle for common utilities
- Single dependency tree reduces conflicts
- Easier refactoring across the codebase

**Trade-offs:**
- Requires discipline to maintain clean boundaries between packages
- Build tooling slightly more complex

---

### <a id="adr-002"></a>ADR-002: PostgreSQL as Primary Database

**Status**: Accepted | **Date**: 2024-01

Use PostgreSQL as the primary relational database with Prisma ORM. Provides strong ACID guarantees, excellent query performance, and rich data types.

**Key Benefits:**
- ACID transactions for order consistency
- Rich query language for complex reporting
- PostGIS extension for geographic features
- Excellent ecosystem and tooling

---

### <a id="adr-003"></a>ADR-003: Multi-Tenant Architecture with Tenant Isolation

**Status**: Accepted | **Date**: 2024-02

Implement a multi-tenant SaaS platform where each tenant's data is logically isolated. Use row-level security (RLS) and schema prefixes for isolation.

**Key Benefits:**
- Single codebase supports multiple customers
- Data isolation for security and compliance
- Easier scaling per-tenant
- Cost-efficient for SaaS model

---

### <a id="adr-004"></a>ADR-004: Fastify for API Layer

**Status**: Accepted | **Date**: 2024-02

Build the backend API with Fastify instead of Express. Fastify provides superior performance, built-in TypeScript support, and modern async/await patterns.

**Key Benefits:**
- 2-3x faster than Express
- Native TypeScript support
- Built-in validation and serialization
- Excellent plugin ecosystem

Gradient-boosted decision trees trained on historical shipment data replace the static ETA formula. Adds Holt-Winters slot demand forecasting for 1–7 day slot utilisation predictions.

**Key Benefits:**
- ETA error reduced from ±35% to <15%
- Captures non-linear interactions (traffic, weather, driver experience)
- Slot demand forecasting prevents overselling during peak periods

### <a id="adr-032"></a>ADR-032: MapLibre GL JS Map Stack

**Status**: Accepted | **Date**: 2026-04

MapLibre GL JS with `@mapbox/mapbox-gl-draw` and `@turf/turf` for all interactive maps in `apps/dashboard`. MapTiler free tier for tiles initially; plan to self-host PMTiles for production. The customer tracking page retains Leaflet.

- ~180 KB gz added only to zones routes via `next/dynamic` boundaries
- Style URL swap behind `<WLMap>` handles future tile provider migration

## Updating ADRs

When circumstances change:

1. **Mark as superseded**: Add status "Superseded by ADR-XXX"
2. **Create new ADR**: Document the new decision and rationale
3. **Update references**: Update related ADRs to reference the new one
4. **Keep history**: Never delete old ADRs (they document why we changed)
